為什麼要從零造？

AI 程式設計的三個階段

AI 輔助程式設計大致經歷了三個階段：程式碼補全（Copilot）→ 聊天助手（Cursor Chat）→ 自主 Agent（Claude Code）。

前兩個階段的共同限制是：模型不能執行操作。它只能給建議，無法自己跑測試看結果。

Claude Code 是一個質的飛躍。你說"給這個專案加使用者註冊功能"，它會自己搜尋路由定義、讀取資料庫模型、建立 handler 檔案、註冊路由、寫測試、執行 npm test、看到失敗、修復、再跑——迴圈十幾次，直到透過為止。

這就是 受控工具迴圈 Agent：模型是決策者，程式碼只是執行環境。

Agent-first 意味著什麼

傳統程式裡，程式碼邏輯決定行為——if/else 都是程式設計師預先寫好的。Agent 架構反過來：模型決定下一步做什麼，程式碼只提供迴圈框架和工具。

整個系統的核心是一個 while (true) 迴圈：

while (true) {
    呼叫模型 → 模型返回響應
    if (響應包含工具呼叫) → 執行工具 → 把結果喂回模型 → 繼續迴圈
    if (響應只是文字) → 任務完成，退出迴圈
}

只有當模型的響應不包含任何工具呼叫時，迴圈才會退出——是模型，而不是程式碼邏輯，決定任務是否完成。

為什麼不直接讀原始碼

Claude Code 的開源快照有 50 萬行 TypeScript：66+ 工具、React/Ink TUI、MCP 協議、OAuth 認證、多代理系統……直接讀很容易迷失在邊界情況和抽象層裡。

我們的做法：只保留最小必要元件，用 ~3400 行程式碼復現核心能力（記憶、技能、多 Agent、許可權規則、分級壓縮、預算控制、Plan Mode），每一步對照真實原始碼講解。就像造卡丁車來理解汽車原理——引擎、方向盤、剎車都在，空調音響先不管。

核心概念速覽

Agent Loop：思考—行動—觀察的迴圈。模型收到請求後決定呼叫哪個工具，系統執行工具並把結果反饋給模型，模型繼續思考，直到不再發出工具呼叫。

工具系統：工具是 Agent 和真實世界互動的橋樑。我們在 System Prompt 裡描述每個工具的名字和引數，模型需要時返回結構化的工具呼叫請求，程式碼執行後把結果喂回去。

上下文工程：模型的表現完全取決於它看到了什麼。上下文視窗有限（200K tokens），但複雜任務可能跑幾十輪——所以需要壓縮。我們實現了 4 級壓縮：裁剪大塊輸出 → 摘要工具結果 → 模型總結整段對話，每級比上一級激進，系統儘量用最輕的方式解決問題。

System Prompt：每次 API 呼叫前組裝的第一條訊息，告訴模型當前作業系統、工作目錄、Git 狀態、專案規則（CLAUDE.md）、可用工具列表。這些上下文直接影響模型的決策質量。

許可權與安全：能執行任意 Shell 命令的 Agent 需要安全控制。我們實現了 5 種許可權模式，從"全部放行"到"全部詢問使用者"——寫檔案前檢查是否允許，危險操作需要確認。

1. Agent Loop — 核心迴圈

本章目標

實現 coding agent 的心臟：一個 while 迴圈，不斷呼叫 LLM → 檢查是否需要執行工具 → 執行工具 → 把結果喂回 LLM → 重複，直到 LLM 認為任務完成。

        C -->|是| D[執行工具]
        D --> E[工具結果推入訊息]
        E --> B
        C -->|否| F[輸出文字<br/>結束迴圈]

Claude Code 怎麼做的

雙層架構

Claude Code 把 Agent Loop 拆成兩層：

  • QueryEngine（~1155 行）：會話級，管整個對話生命週期——使用者輸入處理、USD 預算檢查、Token 統計、會話恢復
  • queryLoop（~1728 行）：單輪級，管一次查詢的執行——訊息壓縮、API 呼叫、工具執行、錯誤恢復

這樣拆的好處是關注點分離：QueryEngine 不需要知道"PTL 錯誤怎麼恢復"，queryLoop 不需要知道"使用者輸入怎麼解析"。

queryLoop：非同步生成器

queryLoop 簽名是 async function*——非同步生成器。選這個而不是回撥/事件的原因：

  1. 背壓控制：消費端不處理完，生產端不繼續，天然防止事件堆積
  1. 線性控制流：所有迴圈分支用普通 continue / break 表達，不需要狀態機

七種 Continue Reason

迴圈有 7 個繼續位置，對應 7 種不同場景：

#名稱觸發場景處理策略
---------------------------
1`next_turn`模型呼叫了工具執行工具，結果推入訊息，繼續
2`collapse_drain_retry`PTL 錯誤，有暫存的摺疊操作提交摺疊釋放空間，重試
3`reactive_compact_retry`PTL 錯誤，摺疊空間不夠強制全量摘要壓縮，重試
4`max_output_tokens_escalate`輸出 Token 截斷，首次升級到更高 Token 限制（16K→64K），重試
5`max_output_tokens_recovery`輸出 Token 截斷，升級不可用注入續寫提示，最多重試 3 次
6`stop_hook_blocking`任務完成但 Stop Hook 攔截繼續執行迴圈
7`token_budget_continuation`API 側 Token 預算耗盡繼續生成

我們的簡化實現只處理第 1 種：有 tool_use 就繼續，否則停。

錯誤扣留策略

這是個值得單獨說的設計：可恢復的錯誤不立即暴露給上層。

當輸出 Token 被截斷時，如果直接 yield 錯誤給 QueryEngine，UI 會顯示報錯——但 queryLoop 後續的恢復邏輯其實能自動處理這個問題。所以 Claude Code 的做法是先"扣留"錯誤，執行恢復邏輯，成功了使用者完全無感知，失敗了才最終暴露。大多數 max_output_tokens 和 prompt_too_long 錯誤都被這樣靜默處理掉了。

並行工具執行

Claude Code 用 StreamingToolExecutor 在 API 流式響應期間並行執行工具：

序列（我們的實現）：
  [========= API 流式響應 =========][tool1][tool2][tool3]

並行（Claude Code）：
  [========= API 流式響應 =========]
       ↑ tool1 的 JSON 完成 → 立即執行
            ↑ tool2 的 JSON 完成 → 立即執行

一個典型 API 響應有 5-30 秒的流式視窗，在這個時間裡多個工具可以併發完成。

// agent.ts — chatAnthropic 方法（核心 Agent Loop）

private async chatAnthropic(userMessage: string): Promise<void> {
  this.anthropicMessages.push({ role: "user", content: userMessage });
  // 在 turn boundary 觸發 auto-compact：此時最後一條訊息是純文字 user，
  // compactAnthropic 內部的 slice(0, -1) 不會切斷 tool_use ↔ tool_result 配對（詳見第 7 章）
  await this.checkAndCompact();

  while (true) {
    if (this.abortController?.signal.aborted) break;

    const response = await this.callAnthropicStream();

    // 累計 token 用量
    this.totalInputTokens += response.usage.input_tokens;
    this.totalOutputTokens += response.usage.output_tokens;
    this.lastInputTokenCount = response.usage.input_tokens;

    // 提取 tool_use block
    const toolUses: Anthropic.ToolUseBlock[] = [];
    for (const block of response.content) {
      if (block.type === "tool_use") toolUses.push(block);
    }

    // assistant 響應推入歷史
    this.anthropicMessages.push({ role: "assistant", content: response.content });

    // 沒有工具呼叫 → 任務完成
    if (toolUses.length === 0) {
      printCost(this.totalInputTokens, this.totalOutputTokens);
      break;
    }

    // 序列執行每個工具
    const toolResults: Anthropic.ToolResultBlockParam[] = [];
    for (const toolUse of toolUses) {
      if (this.abortController?.signal.aborted) break;

      const input = toolUse.input as Record<string, any>;
      printToolCall(toolUse.name, input);

      // 許可權檢查（詳見第 6 章）
      const perm = checkPermission(toolUse.name, input, this.permissionMode, this.planFilePath);
      if (perm.action === "deny") {
        toolResults.push({ type: "tool_result", tool_use_id: toolUse.id,
          content: `Action denied: ${perm.message}` });
        continue;
      }
      if (perm.action === "confirm" && perm.message && !this.confirmedPaths.has(perm.message)) {
        const confirmed = await this.confirmDangerous(perm.message);
        if (!confirmed) {
          toolResults.push({ type: "tool_result", tool_use_id: toolUse.id,
            content: "User denied this action." });
          continue;
        }
        this.confirmedPaths.add(perm.message);
      }

      const result = await executeTool(toolUse.name, input);
      printToolResult(toolUse.name, result);
      toolResults.push({ type: "tool_result", tool_use_id: toolUse.id, content: result });
    }

    // 工具結果以 user 訊息推入（Anthropic API 要求）
    this.anthropicMessages.push({ role: "user", content: toolResults });
  }
}

訊息陣列的增長方式

理解 Agent Loop 的關鍵：訊息陣列是怎麼增長的。

第 1 輪:
  messages = [
    { role: "user",      content: "幫我修復 bug" }
    { role: "assistant", content: [text + tool_use(read_file)] }
    { role: "user",      content: [tool_result("檔案內容...")] }
  ]

第 2 輪（LLM 看到檔案內容後決定編輯）:
  messages = [
    ...前 3 條,
    { role: "assistant", content: [text + tool_use(edit_file)] }
    { role: "user",      content: [tool_result("編輯成功")] }
  ]

第 3 輪（LLM 認為任務完成）:
  messages = [
    ...前 5 條,
    { role: "assistant", content: [text("已修復!")] }  ← 無 tool_use → break
  ]

edit_file 的核心設計

FileEditTool 執行前有 14 步驗證（按 I/O 成本排序：先檢查記憶體狀態，再訪問磁碟），其中最關鍵的三個：

讀取前置檢查：程式碼層面的強制約束，不只是 prompt 建議。未先讀取檔案則拒絕執行，確保模型基於檔案當前狀態編輯而非過時記憶。

外部修改檢測：透過 mtime 檢測檔案在讀取後是否被外部修改（比如使用者在 IDE 中編輯了同一個檔案），解決真實競爭條件。

配置檔案保護：對 .claude/settings.json 等，驗證會模擬執行編輯後做 JSON Schema 校驗，防止看似合理的編輯損壞配置格式。

為什麼用 search-and-replace

在確定 search-and-replace 之前，有幾種備選方案：

方案致命缺陷
---------------
行號編輯位置相關：第一次插入 3 行後，後續所有行號偏移，多步編輯需要複雜重算

  new_string: string;

}

function normalizeQuotes(s: string): string {
  return s
    .replace(/[\u2018\u2019\u2032]/g, "'")   // curly single → straight
    .replace(/[\u201C\u201D\u2033]/g, '"');   // curly double → straight
}

function findActualString(fileContent: string, searchString: string): string | null {
  if (fileContent.includes(searchString)) return searchString;
  const normSearch = normalizeQuotes(searchString);
  const normFile = normalizeQuotes(fileContent);
  const idx = normFile.indexOf(normSearch);
  if (idx !== -1) return fileContent.substring(idx, idx + searchString.length);
  return null;
}

  pattern: string;
  path?: string;
  include?: string;
}): string {

    if (input.include) args.push(`--include=${input.include}`);
    args.push(input.pattern);

      timeout: 10000,

def _grep_search(inp: dict) -> str:
    pattern = inp["pattern"]
    path = inp.get("path") or "."
    include = inp.get("include")

    try:
        args = ["grep", "--line-number", "--color=never", "-r"]
        if include:
            args.append(f"--include={include}")
        args.extend(["--", pattern, path])
        result = subprocess.run(args, capture_output=True, text=True, timeout=10)
        if result.returncode == 1:
            return "No matches found."
        if result.returncode != 0:
            return f"Error: {result.stderr}"
        lines = [l for l in result.stdout.split("\n") if l]
        output = "\n".join(lines[:100])
        if len(lines) > 100:
            output += f"\n... and {len(lines) - 100} more matches"
        return output
    except Exception as e:
        return f"Error: {e}"

--color=never 禁用 ANSI 顏色程式碼（輸出給模型看的，不需要顏色）。Python 版本的 -- 分隔符確保以 - 開頭的 pattern 不被誤解析為 grep 選項。

      text = text
        .replace(/<script[\s\S]*?<\/script>/gi, "")
        .replace(/<style[\s\S]*?<\/style>/gi, "")
        .replace(/<[^>]*>/g, " ")
        .replace(/&nbsp;/g, " ").replace(/&amp;/g, "&")
        .replace(/\s{2,}/g, " ").replace(/\n{3,}/g, "\n\n").trim();
    }
    if (text.length > maxLength) {
      text = text.slice(0, maxLength) + `\n\n[... truncated at ${maxLength} characters]`;
    }
    result = text || "(empty response)";

    result = err.name === "AbortError"

Read-before-edit + mtime 防護

Claude Code 的一個重要安全機制：編輯檔案前必須先讀取。這防止模型在不瞭解檔案當前內容的情況下盲目修改，同時檢測外部修改避免覆蓋使用者的手動編輯。

TypeScript

// tools.ts — executeTool 中的 mtime 追蹤

export async function executeTool(
  name: string,
  input: Record<string, any>,
  readFileState?: Map<string, number>  // filepath → mtimeMs
): Promise<string> {
  switch (name) {
    case "read_file":
      result = readFile(input as { file_path: string });
      // 記錄檔案的修改時間
      if (readFileState && !result.startsWith("Error")) {
        const absPath = resolve(input.file_path);
        try { readFileState.set(absPath, statSync(absPath).mtimeMs); } catch {}
      }
      break;

    case "write_file": {
      const absPath = resolve(input.file_path);
      // 已存在的檔案必須先 read
      if (readFileState && existsSync(absPath)) {
        if (!readFileState.has(absPath)) {
          return "Error: You must read this file before writing. Use read_file first.";
        }
        // mtime 變化說明檔案被外部修改
        const cur = statSync(absPath).mtimeMs;
        if (cur !== readFileState.get(absPath)!) {
          return "Warning: file was modified externally. Please read_file again.";
        }
      }
      result = writeFile(input as { file_path: string; content: string });
      // 更新 mtime
      if (readFileState && !result.startsWith("Error")) {
        try { readFileState.set(absPath, statSync(absPath).mtimeMs); } catch {}
      }
      break;
    }
    // edit_file 同理...
  }
}

三個關鍵點：

  • readFileState Map 在 Agent 例項中維護，key 是絕對路徑，value 是上次讀取時的 mtimeMs
  • 新檔案跳過檢查：existsSync(absPath) 為 false 時不強制先讀——建立新檔案不需要先讀
  • mtime 比較：讀取時記錄 mtime，寫入前比較。如果不一致，說明檔案在 Agent 讀取後被使用者或其他程序修改了，返回警告而非靜默覆蓋

這與 Claude Code 的 readFileTimestamps 機制對齊——編輯必須基於已知狀態，不能"盲寫"。

// tool_search 執行：匹配 → 啟用 → 返回 schema
case "tool_search": {
  const query = (input.query as string || "").toLowerCase();
  const deferred = toolDefinitions.filter(t => t.deferred);
  const matches = deferred.filter(t =>
    t.name.toLowerCase().includes(query) ||
    (t.description || "").toLowerCase().includes(query)
  );
  if (matches.length === 0) return "No matching deferred tools found.";
  for (const m of matches) activatedTools.add(m.name);
  return JSON.stringify(matches.map(t => ({
    name: t.name, description: t.description, input_schema: t.input_schema,
  })), null, 2);
}

工作流程：

  1. API 呼叫時，getActiveToolDefinitions() 過濾掉未啟用的 deferred 工具（只發名稱，不發 schema）
  1. System prompt 中透過 getDeferredToolNames() 告知模型哪些工具可以透過 tool_search 啟用
  1. 模型需要時呼叫 tool_search，匹配的工具被加入 activatedTools Set
  1. 下一次 API 呼叫自動包含已啟用工具的完整 schema

我們只有 2 個 deferred 工具（plan mode），但這個機制對擴充套件到 20+ 工具時至關重要。

Claude Code 怎麼做的

Claude Code 的 System Prompt 不是隨意堆砌的指令，而是經過大量 A/B 測試和模型行為觀察迭代打磨的工程產物。

7 層遞進結構

提示詞從抽象到具體分為 7 層——先建立身份和約束框架，再填充具體行為指導。這個順序很重要：模型先建立的概念會成為理解後續內容的框架。

1. Identity   → 我是誰？interactive agent
2. System     → 執行環境的基本事實
3. Doing Tasks → 怎麼寫程式碼？（反模式接種）
4. Actions    → 哪些操作需要確認？（爆炸半徑框架）
5. Using Tools → 怎麼用工具？（偏好對映表）
6. Tone & Style → 輸出什麼格式？
7. Output Efficiency → 怎麼更簡潔？

反模式接種

明確告訴模型"不要做什麼"，比只描述"要做什麼"有效得多。

正面指令（"be concise"）給模型留下了自我合理化的空間——它會認為"加註釋是讓程式碼更簡潔易讀的"，然後給每個函式加 docstring。而負面指令（"don't add docstrings to code you didn't change"）消除了解釋餘地。

Claude Code 的 Doing Tasks 部分有三條精確的"不要"：

  • 不要擴大範圍：修 bug 不需要順手重構周圍程式碼
  • 不要防禦性程式設計：不為不可能發生的場景加 try-catch 和校驗
  • 不要過早抽象："Three similar lines of code is better than a premature abstraction"

這些規則的價值不在概念（誰都知道"不要過度工程"），而在措辭的精確度——給了模型具體的判斷標準，而非模糊的原則。

爆炸半徑框架

Actions 部分沒有羅列"不能做 X、Y、Z"，而是教給模型一個風險評估框架：

Carefully consider the reversibility and blast radius of actions.

二維模型：可逆性 × 影響範圍。高風險 = 不可逆 + 影響共享環境（force push、刪除雲資源）；低風險 = 可逆 + 隻影響本地（編輯本地檔案）。

這比窮舉規則擴充套件性強得多——模型遇到規則列表之外的新場景（比如呼叫 API 刪除雲資源）能自行推理，而不是不知道怎麼做。

還有一條關鍵規則：使用者批准一次操作，不等於批准所有類似操作。每次授權只對當前範圍有效。

工具偏好對映表

Claude Code 在提示詞中明確要求模型用專用工具而非 bash 命令：

Use Read instead of cat/head/tail
Use Edit instead of sed/awk
Use Glob instead of find/ls
Use Grep instead of grep/rg

專用工具和 bash 命令底層功能差不多，差異在使用者體驗：許可權可以細粒度控制（讀取 vs 寫入分開授權）、輸出結構化、原生支援並行呼叫。沒有這張對映表，模型會預設用訓練資料中出現最多的方式——即各種 bash 命令。

CLAUDE.md 層級發現

CLAUDE.md 是專案級指令檔案，類似 .eslintrc 但面向 AI。Claude Code 從 5 個位置載入：全域性管理策略 → 使用者主目錄 → 專案目錄（CWD 向上遍歷）→ 本地檔案 → 命令列指定目錄。

靠近 CWD 的檔案後載入、優先順序更高——利用 LLM 的近因效應，子目錄規則可以覆蓋父目錄規則。

TypeScript

// prompt.ts — @include 解析

const INCLUDE_REGEX = /^@(\.\/[^\s]+|~\/[^\s]+|\/[^\s]+)$/gm;
const MAX_INCLUDE_DEPTH = 5;

function resolveIncludes(
  content: string,
  basePath: string,
  visited: Set<string> = new Set(),
  depth: number = 0
): string {
  if (depth >= MAX_INCLUDE_DEPTH) return content;
  return content.replace(INCLUDE_REGEX, (_match, rawPath: string) => {
    let resolved: string;
    if (rawPath.startsWith("~/")) {
      resolved = join(os.homedir(), rawPath.slice(2));
    } else if (rawPath.startsWith("/")) {
      resolved = rawPath;
    } else {
      resolved = resolve(basePath, rawPath);  // ./relative
    }
    resolved = resolve(resolved);
    if (visited.has(resolved)) return `<!-- circular: ${rawPath} -->`;
    if (!existsSync(resolved)) return `<!-- not found: ${rawPath} -->`;
    try {
      visited.add(resolved);
      const included = readFileSync(resolved, "utf-8");
      return resolveIncludes(included, dirname(resolved), visited, depth + 1);
    } catch {
      return `<!-- error reading: ${rawPath} -->`;
    }
  });
}

三種路徑格式：

  • @./relative/path — 相對於當前 CLAUDE.md 所在目錄
  • @~/path — 相對於使用者 home 目錄
  • @/absolute/path — 絕對路徑

防護措施：

  • visited Set 防止迴圈引用（A include B，B include A）
  • MAX_INCLUDE_DEPTH = 5 防止巢狀過深
  • 找不到檔案時留下 HTML 註釋標記，不報錯中斷

// prompt.ts — 規則目錄載入

function loadRulesDir(dir: string): string {
  const rulesDir = join(dir, ".claude", "rules");
  if (!existsSync(rulesDir)) return "";
  const files = readdirSync(rulesDir).filter(f => f.endsWith(".md")).sort();
  const parts: string[] = [];
  for (const file of files) {
    let content = readFileSync(join(rulesDir, file), "utf-8");
    content = resolveIncludes(content, rulesDir);  // 規則檔案也支援 @include
    parts.push(`<!-- rule: ${file} -->\n${content}`);
  }
  return parts.length > 0 ? "\n\n## Rules\n" + parts.join("\n\n") : "";
}

Claude Code 怎麼做的

Claude Code 的入口是 src/entrypoints/cli.tsx——用 React/Ink 把元件模型搬進終端，支援流式 Markdown 渲染、Vim 模式、多 Tab、鍵盤自定義。會話用 JSONL 格式追加寫入，崩潰安全。

終端原生 vs GUI

這是一個主動選擇。開發者的工作流在終端裡，開啟瀏覽器意味著上下文切換。終端原生就是另一個命令列工具，跟 git、grep 一樣嵌入到已有工作流。具體好處：SSH 環境可用、可接管道 (echo "fix" | claude)、支援 tmux 多例項並行、記憶體開銷接近零。

中斷成本遠低於撤銷成本。使用者在 Agent 走錯方向前 3 秒就能按 Ctrl+C，而不是等 20 秒執行完再花更多時間撤銷。每個工具有 4 種渲染方法（開始/完成/被拒/報錯），長時間執行的工具實時流式輸出 stdout，而不是等完成才展示。

JSONL 會話儲存

整體 JSON 覆蓋寫入有兩個問題：寫入中途崩潰會損壞整個檔案；對話越長每次儲存越慢。

JSONL 每輪追加一行，O(1) 寫入，崩潰最多丟最後一行。檔案系統的 append 操作通常是原子的。恢復時逐行解析，跳過末尾不完整的行即可。

// cli.ts — runRepl

async function runRepl(agent: Agent) {
  const rl = readline.createInterface({ input: process.stdin, output: process.stdout });

  let sigintCount = 0;
  process.on("SIGINT", () => {
    if (agent.isProcessing) {
      agent.abort();
      console.log("\n  (interrupted)");
      sigintCount = 0;
      printUserPrompt();
    } else {
      sigintCount++;
      if (sigintCount >= 2) { console.log("\nBye!\n"); process.exit(0); }
      console.log("\n  Press Ctrl+C again to exit.");
      printUserPrompt();
    }
  });

  printWelcome();

  // rl.once 而非 rl.on：保證嚴格序列，避免多個 chat 併發修改訊息歷史
  const askQuestion = (): void => {
    printUserPrompt();
    rl.once("line", async (line) => {
      const input = line.trim();
      sigintCount = 0;

      if (!input) { askQuestion(); return; }
      if (input === "exit" || input === "quit") { console.log("\nBye!\n"); process.exit(0); }

      if (input === "/clear") { agent.clearHistory(); askQuestion(); return; }
      if (input === "/cost")  { agent.showCost(); askQuestion(); return; }
      if (input === "/compact") {
        try { await agent.compact(); } catch (e: any) { printError(e.message); }
        askQuestion(); return;
      }
      if (input === "/plan") { agent.togglePlanMode(); askQuestion(); return; }

      try {
        await agent.chat(input);
      } catch (e: any) {
        if (e.name !== "AbortError" && !e.message?.includes("aborted")) printError(e.message);
      }

      askQuestion();
    });
  };

  askQuestion();
}

Ctrl+C 的雙重語義：處理中按下 → 中斷當前操作，回到輸入提示；空閒時按下 → 第一次提醒，第二次退出。這避免了兩種意外：手滑 Ctrl+C 導致整個會話丟失，以及 Agent 跑偏時只能眼睜睜等它跑完。

rl.once vs rl.on：rl.on 註冊的 handler 不會等 await agent.chat() 完成就響應下一行輸入，導致多個 chat 併發修改訊息歷史。rl.once 每次只監聽一行，處理完再遞迴註冊，天然序列。Python 的 while + input() + await 沒有這個問題。

Claude Code 怎麼做的

為什麼需要流式輸出？

模型生成速度大約每秒 30-80 個 token，稍長的回答需要 10-30 秒。使用者面對空白等待的容忍極限約 2-3 秒。流式輸出讓第一個字在幾百毫秒內出現，把"等待 30 秒"變成"看著內容逐漸寫出來"——主觀等待感接近零，並且使用者能在方向錯誤時提前中斷。

底層用的是 SSE（Server-Sent Events）：服務端用一條持久 HTTP 連線持續推送 data: 行，每幾個 token 就推一個 content_block_delta 事件。比 WebSocket 簡單，對 LLM 應用來說單向推送已經夠用。

流式處理與並行工具執行

Claude Code 的一個關鍵最佳化：StreamingToolExecutor 在模型還在生成後續內容時，已解析完成的 tool_use block 就立即開始執行。序列方式下工具執行只能等 API 完整響應後開始；流式並行下，第一個 tool_use 解析完畢時直接分發，不等第二個。

在典型的 5-30 秒 API 流視窗內，檔案讀取（< 100ms）幾乎能全部覆蓋進去——流結束時工具結果往往已全部就緒。

錯誤重試

不是所有錯誤都值得重試：429/503/529 和網路瞬斷（ECONNRESET）可以重試；400/401/404 反映程式碼或配置問題，重試沒有意義。

指數退避（而不是固定間隔）的原因：服務過載時，大量客戶端固定 1 秒後同時重試會形成"重試風暴"，反而加劇過載。指數退避讓間隔逐輪翻倍（1s → 2s → 4s），加上隨機抖動打破多客戶端同步，是標準的分散式容錯做法。

// agent.ts — callOpenAIStream

private async callOpenAIStream(): Promise<OpenAI.ChatCompletion> {
  return withRetry(async (signal) => {
    const stream = await this.openaiClient!.chat.completions.create({
      model: this.model,
      max_tokens: 16384,
      tools: toOpenAITools(),
      messages: this.openaiMessages,
      stream: true,
      stream_options: { include_usage: true },
    }, { signal });

    let content = "";
    let firstText = true;
    const toolCalls: Map<number, { id: string; name: string; arguments: string }> = new Map();
    let finishReason = "";
    let usage: { prompt_tokens: number; completion_tokens: number } | undefined;

    for await (const chunk of stream) {
      const delta = chunk.choices[0]?.delta;

      if (chunk.usage) {
        usage = { prompt_tokens: chunk.usage.prompt_tokens, completion_tokens: chunk.usage.completion_tokens };
      }

      if (!delta) continue;

      if (delta.content) {
        if (firstText) { printAssistantText("\n"); firstText = false; }
        printAssistantText(delta.content);
        content += delta.content;
      }

      // tool_calls 引數分片到達，按 index 累積
      if (delta.tool_calls) {
        for (const tc of delta.tool_calls) {
          const existing = toolCalls.get(tc.index);
          if (existing) {
            if (tc.function?.arguments) existing.arguments += tc.function.arguments;
          } else {
            toolCalls.set(tc.index, {
              id: tc.id || "",
              name: tc.function?.name || "",
              arguments: tc.function?.arguments || "",
            });
          }
        }
      }

      if (chunk.choices[0]?.finish_reason) finishReason = chunk.choices[0].finish_reason;
    }

    const assembledToolCalls = toolCalls.size > 0
      ? Array.from(toolCalls.entries())
          .sort(([a], [b]) => a - b)
          .map(([_, tc]) => ({
            id: tc.id, type: "function" as const,
            function: { name: tc.name, arguments: tc.arguments },
          }))
      : undefined;

    return {
      id: "stream", object: "chat.completion", created: Date.now(), model: this.model,
      choices: [{
        index: 0,
        message: { role: "assistant" as const, content: content || null, tool_calls: assembledToolCalls, refusal: null },
        finish_reason: finishReason || "stop", logprobs: null,
      }],
      usage: usage || { prompt_tokens: 0, completion_tokens: 0, total_tokens: 0 },
    } as OpenAI.ChatCompletion;
  }, this.abortController?.signal);
}

重試機制

TypeScript

function isRetryable(error: any): boolean {
  const status = error?.status || error?.statusCode;
  if ([429, 503, 529].includes(status)) return true;
  if (error?.code === "ECONNRESET" || error?.code === "ETIMEDOUT") return true;
  if (error?.message?.includes("overloaded")) return true;
  return false;
}

async function withRetry<T>(
  fn: (signal?: AbortSignal) => Promise<T>,
  signal?: AbortSignal,
  maxRetries = 3
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(signal);
    } catch (error: any) {
      if (signal?.aborted) throw error;
      if (attempt >= maxRetries || !isRetryable(error)) throw error;
      const delay = Math.min(1000 * Math.pow(2, attempt), 30000) + Math.random() * 1000;
      const reason = error?.status ? `HTTP ${error.status}` : error?.code || "network error";
      printRetry(attempt + 1, maxRetries, reason);
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}

    for attempt in range(max_retries + 1):
        try:
            return await fn()
        except Exception as error:

設計要點：

  • content_block_stop 是 block 級別事件：當單個 tool_use block 的 JSON 完整接收時觸發，並非整個響應結束。模型可能在一次響應中返回多個工具呼叫，第一個 block 完整時第二個可能還在流式傳輸中
  • 僅併發安全工具提前執行：只有只讀工具（read_file、list_files、grep_search、web_fetch）會被提前執行，寫操作和命令執行不會
  • 許可權檢查仍然生效：只有 checkPermission 返回 "allow" 的工具才會提前執行，需要使用者確認的工具（"confirm"）不會被提前觸發
  • Promise/Task 儲存，後續直接 await：earlyExecutions Map 儲存的是 Promise（TS）或 Task（Python），後續工具處理迴圈檢查到已有提前執行的結果時，直接 await 即可——通常此時已經完成
  • 核心收益：5-30 秒的流式視窗期內，工具執行與模型生成並行進行，檔案讀取等快速操作在流結束時往往已經就緒

6. 許可權與安全

本章目標

實現完整的許可權安全機制：危險命令檢測 → 可配置的 allow/deny 許可權規則 → 統一許可權檢查 → 會話級白名單 → 使用者確認對話方塊。從"寫死的規則"到"使用者定義規則"，讓 agent 自動放行安全操作、自動攔截危險操作，無需每次手動確認。

核心思路：多層檢查，deny 優先。許可權模式（全域性策略）→ 配置檔案規則（Layer 1）→ 內建危險模式檢測（Layer 2）→ 會話白名單 → 使用者確認。

Claude Code 怎麼做的

Claude Code 在真實環境執行程式碼——讀寫檔案、執行 Shell、操作 Git。安全機制不到位，一條 rm -rf / 就能造成災難。因此它採用了縱深防禦（Defense in Depth）：7 個獨立的安全層，即使某一層被繞過，其他層仍然有效。

7 層縱深防禦

層機制核心作用
-------------------
1Trust Dialog首次進入目錄時確認信任，防止惡意專案的 Hook 自動執行
2許可權模式全域性策略開關（default/plan/acceptEdits/bypassPermissions/dontAsk）
3許可權規則匹配allow/deny/ask 規則，8 個來源，優先順序從企業策略到會話級
4Bash AST 分析tree-sitter 解析命令為 AST，23 項靜態安全檢查，FAIL-CLOSED 原則
5工具級驗證validateInput + checkPermissions，保護危險檔案路徑和路徑邊界
6沙箱隔離macOS Seatbelt / Linux namespace，限制檔案系統和網路訪問範圍
7使用者確認互動對話方塊 + Hook + ML 分類器競速，第一個決定生效

幾個值得了解的設計細節：

bypassPermissions（--yolo）並不是真的繞過一切。原始碼檢查順序是：先檢查 deny 規則（命中直接拒絕）→ 再檢查 bypass-immune 路徑（.git/、.claude/ 等仍需確認）→ 最後才跳過普通確認。管理員透過 deny 規則可以對 --yolo 施加約束。

Layer 4 為什麼不用正則：Shell 語法複雜，正則面對 echo hello$(rm -rf /) 這類命令會看到的是 echo hello，實際執行的卻是 rm -rf /。tree-sitter 真正解析 AST，不理解的結構（命令替換、變數展開、控制流等）一律標記為 too-complex，要求使用者確認。

8 種規則來源，嚴格優先順序：企業 MDM 策略（不可覆蓋）> 使用者全域性 > 專案級（提交到倉庫）> 本地專案（不提交）> CLI 引數 > 執行時引數 > 命令定義 > 會話級（點"始終允許"產生）。低優先順序不能覆蓋高優先順序——企業策略 deny 的操作，使用者在任何層級寫 allow 都無效。

3 種匹配型別：精確匹配（Bash(git status)）、字首匹配（Bash(npm:)）、萬用字元匹配（Bash(git --no-verify)）。萬用字元以空格+* 結尾時尾部可選，與字首語法行為保持一致。

Layer 7 的競速機制：UI 對話方塊、PermissionRequest Hook、ML 分類器三者同時啟動，createResolveOnce 守衛確保只有第一個決定生效。一旦使用者觸碰對話方塊，Hook 和分類器的結果一律被丟棄——人類意圖永遠優先。對話方塊還有 200ms 防誤觸寬限期。

拒絕追蹤：連續拒絕 3 次觸發降級（auto 模式回退到互動確認），總拒絕 20 次中止 Agent 執行——防止模型陷入反覆嘗試被拒絕操作的死迴圈。

我們的實現

把 7 層簡化為 4 層：危險命令檢測、許可權規則系統、統一許可權檢查、會話級白名單。8 種規則來源簡化為 2 種（使用者級 + 專案級），3 種規則行為簡化為 2 種（allow + deny）。

2. 許可權規則系統

除內建危險檢測外，支援透過配置檔案預定義 allow/deny 規則，讓 agent 自動放行安全操作、自動攔截危險操作。

規則解析（parseRule）

把字串規則拆成結構化資料。run_shell(npm test) → {tool: "run_shell", pattern: "npm test"}，裸工具名 → {tool: "read_file", pattern: null}。

TypeScript

// tools.ts

interface ParsedRule {
  tool: string;
  pattern: string | null;  // null 表示匹配該工具的所有呼叫
}

function parseRule(rule: string): ParsedRule {
  const match = rule.match(/^([a-z_]+)\((.+)\)$/);
  if (match) {
    return { tool: match[1], pattern: match[2] };
  }
  return { tool: rule, pattern: null };
}

規則匹配（matchesRule）

三層判斷：工具名不匹配直接跳過 → 無 pattern 則工具名匹配即可 → 有 pattern 則取 command 或 file_path 做匹配。支援兩種匹配方式：尾部 * 做字首匹配，否則精確匹配。

TypeScript

// tools.ts

function matchesRule(
  rule: ParsedRule,
  toolName: string,
  input: Record<string, any>
): boolean {
  if (rule.tool !== toolName) return false;
  if (!rule.pattern) return true;

  let value = "";
  if (toolName === "run_shell") value = input.command || "";
  else if (input.file_path) value = input.file_path;
  else return true;

  const pattern = rule.pattern;
  if (pattern.endsWith("*")) {
    return value.startsWith(pattern.slice(0, -1));
  }
  return value === pattern;
}

  toolName: string,

3. 統一許可權檢查

checkPermission 是許可權系統的統一入口，整合了許可權模式、配置檔案規則和內建危險檢測，返回 {action, message}，action 三種值：allow、deny、confirm。

優先順序：deny 規則 > allow 規則 > 模式邏輯 > 內建危險檢測 > 預設允許。

TypeScript

// tools.ts — checkPermission

export function checkPermission(
  toolName: string,
  input: Record<string, any>,
  mode: PermissionMode = "default",
  planFilePath?: string
): { action: "allow" | "deny" | "confirm"; message?: string } {
  if (mode === "bypassPermissions") return { action: "allow" };

  // Layer 1: 配置檔案規則（deny 優先）
  const ruleResult = checkPermissionRules(toolName, input);
  if (ruleResult === "deny") {
    return { action: "deny", message: `Denied by permission rule for ${toolName}` };
  }
  if (ruleResult === "allow") {
    return { action: "allow" };
  }

  // 讀工具永遠安全
  if (READ_TOOLS.has(toolName)) return { action: "allow" };

  // 許可權模式檢查
  if (mode === "plan") {
    if (EDIT_TOOLS.has(toolName)) {
      const filePath = input.file_path || input.path;
      if (planFilePath && filePath === planFilePath) return { action: "allow" };
      return { action: "deny", message: `Blocked in plan mode: ${toolName}` };
    }
    if (toolName === "run_shell") {
      return { action: "deny", message: "Shell commands blocked in plan mode" };
    }
  }

  if (mode === "acceptEdits" && EDIT_TOOLS.has(toolName)) {
    return { action: "allow" };
  }

  // Layer 2: 內建危險模式檢查
  let needsConfirm = false;
  let confirmMessage = "";

  if (toolName === "run_shell" && isDangerous(input.command)) {
    needsConfirm = true;
    confirmMessage = input.command;
  } else if (toolName === "write_file" && !existsSync(input.file_path)) {
    needsConfirm = true;
    confirmMessage = `write new file: ${input.file_path}`;
  } else if (toolName === "edit_file" && !existsSync(input.file_path)) {
    needsConfirm = true;
    confirmMessage = `edit non-existent file: ${input.file_path}`;
  }

  if (needsConfirm) {
    if (mode === "dontAsk") {
      return { action: "deny", message: `Auto-denied (dontAsk mode): ${confirmMessage}` };
    }
    return { action: "confirm", message: confirmMessage };
  }

  return { action: "allow" };
}

Claude Code 怎麼做的

上下文構建

每次 API 呼叫前，Claude Code 把三類資訊組裝進請求：

系統提示詞是最穩定的部分，由歸屬頭、工具 schema、安全規則等拼接而成。其中有一個 SYSTEM_PROMPT_DYNAMIC_BOUNDARY 哨兵將其分為靜態半區和動態半區——靜態半區對所有使用者完全相同，標記 scope: 'global' 全球共享快取；動態半區（MCP 工具、語言偏好等）因使用者而異，不共享。這讓全球數百萬使用者共享同一份核心系統提示詞的快取，是主要的成本最佳化手段之一。

系統/使用者上下文每會話計算一次並 memoize：git 狀態（5 個命令並行執行）、CLAUDE.md 檔案（從 CWD 向上遍歷目錄樹）、當前日期等。注入順序是刻意安排的——系統上下文後置於系統提示詞，使用者上下文前置於訊息陣列，確保最穩定的內容在最前面，最大化快取命中。

訊息歷史記錄對話中的一切，是壓縮管道的主要操作物件。傳送給 API 前會經過 normalizeMessagesForAPI() 修復格式問題：附件重排序、處理 thinking 塊、合併分裂訊息、驗證 tool_use/tool_result 配對等。

5 級壓縮流水線

設計哲學是漸進式壓縮：先用成本最低的手段，只在必要時才動更重的武器。

Level 1: Tool Result 預算裁剪 — 工具宣告 maxResultSizeChars（預設 50K 字元），超限時持久化到磁碟，上下文中只保留緊湊引用和 2KB 預覽。選擇持久化而非截斷的原因：資料沒有丟失，模型可以隨時用 Read 工具讀取完整檔案。

Level 2: History Snip — Feature-gated 功能，裁剪歷史中的冗餘部分。釋放的量會傳遞給後續 autocompact 的閾值計算，因為 snip 移除訊息後最後一條 assistant 訊息的 usage 仍反映 snip 前的大小，不修正會導致 autocompact 過早觸發。

Level 3: Microcompact — 清理不再需要的舊工具結果，有兩條路徑：

  • 快取已冷（空閒超過 N 分鐘）：直接修改訊息內容，將舊工具結果替換為佔位符。快取過期了，修改不會造成額外失效。
  • 快取仍熱：使用 API 級的 cache_edits 機制在服務端就地刪除，完全不修改本地訊息，避免快取字首失效。

Level 4: Context Collapse — 投影式摺疊，關鍵特性是不修改原始訊息，只建立一個摺疊檢視。類比資料庫 View：底層表不變，查詢時看到過濾後的結果。啟用時會抑制 Autocompact，避免兩者競爭。

Level 5: Autocompact — 最後手段，fork 子 Agent 呼叫 API 生成摘要。觸發閾值約 85.5% 上下文利用率。壓縮提示詞用"分析-摘要"兩階段：先讓模型在 塊推理，再生成標準化的

（9 個部分），最後剝離推理過程只保留摘要——典型的鏈式思考草稿技術。

Token 預算與快取

Token 估算從不呼叫額外 API：用最近一次 API 返回的 usage 作為錨點，新增訊息用字元數 / 4 粗估。誤差從純估算的 30%+ 降到 <5%。

Prompt 快取脆弱性在於字首中任何位元組變化都會導致失效。Claude Code 在多個層面維護穩定性：靜態/動態邊界標記、beta header 粘性鎖存（一旦傳送就持續出現，不隨 feature flag 變化）、工具陣列末尾打快取斷點、以及斷裂檢測（cache_read_input_tokens 下降 >5% 時自動歸因）。

熔斷器：曾有會話連續 autocompact 失敗 3,272 次，浪費大量 API 呼叫。現在連續 3 次失敗後直接停止重試。

與 Claude Code 的區別：Claude Code 持久化到磁碟，模型後續可用 Read 工具取回完整內容。我們現在也實現了持久化——見下方 persistLargeResult。兩層配合：persistLargeResult 先攔截 >30KB 的結果儲存到磁碟，truncateResult 再處理透過第一層但仍超過 50K 的內容。

第 0.5 層：大結果持久化（persistLargeResult）

當工具返回結果超過 30KB 時，將完整內容寫入磁碟，上下文中只保留預覽和檔案路徑。模型後續可以用 read_file 按需取回完整輸出。

// agent.ts — persistLargeResult

private persistLargeResult(toolName: string, result: string): string {
  const THRESHOLD = 30 * 1024; // 30 KB
  if (Buffer.byteLength(result) <= THRESHOLD) return result;

  const dir = join(homedir(), ".mini-claude", "tool-results");
  mkdirSync(dir, { recursive: true });
  const filename = `${Date.now()}-${toolName}.txt`;
  const filepath = join(dir, filename);
  writeFileSync(filepath, result);

  const lines = result.split("\n");
  const preview = lines.slice(0, 200).join("\n");
  const sizeKB = (Buffer.byteLength(result) / 1024).toFixed(1);

  return `[Result too large (${sizeKB} KB, ${lines.length} lines). Full output saved to ${filepath}. You can use read_file to see the full result.]\n\nPreview (first 200 lines):\n${preview}`;
}

這一層的設計要點：

  • 30KB 閾值低於 truncateResult 的 50K 限制：在截斷髮生之前先攔截大結果，避免不可逆的資訊丟失。如果一個結果有 80KB，persistLargeResult 會先將完整內容儲存到磁碟，返回預覽；而不是等 truncateResult 把中間部分永久丟棄。
  • 200 行預覽：給模型足夠的上下文來判斷是否需要讀取完整輸出。大多數情況下，前 200 行已經包含了關鍵資訊（檔案列表的開頭、搜尋結果的前幾個匹配、命令輸出的主要內容）。
  • 可恢復 vs 不可恢復：這是與 truncateResult 的根本區別。truncateResult 是不可逆的——被截掉的內容永遠消失了。persistLargeResult 把資料儲存到 ~/.mini-claude/tool-results/{timestamp}-{toolName}.txt，模型隨時可以用 read_file 取回。
  • 呼叫時機：在主迴圈中每次工具執行完成後、結果新增到訊息之前呼叫。這意味著它在 truncateResult 之前生效——先嚐試儲存，儲存後返回的預覽文字通常遠小於 50K，不會再觸發截斷。
  • 與 Claude Code 的對齊：這一設計直接對應 Claude Code 的 Level 1 策略（持久化到磁碟，上下文中只保留引用）。區別在於 Claude Code 用 2KB 預覽，我們用 200 行——思路相同，實現簡化。

private budgetToolResultsAnthropic(): void {

Claude Code 怎麼做的

Claude Code 記憶系統的核心約束只有一條：只記憶不可從當前專案狀態推導的資訊。程式碼模式、架構、檔案路徑、git 歷史、正在進行的除錯——這些讀程式碼和 git log 就能獲得，記憶中的版本只會製造漂移。連使用者明確要求儲存的資訊也不例外——如果使用者說"記住這個 PR 列表"，Agent 應該追問：列表中有什麼是不可推導的？某個截止日期？某個意外發現？

記憶分四種型別：

型別記什麼觸發時機
-----------------------
**user**使用者身份、偏好、知識背景瞭解到使用者角色/偏好時
**feedback**對 Agent 行為的糾正**和肯定**使用者糾正或肯定某個行為時
**project**專案進展、決策、截止日期瞭解到專案動態時
**reference**外部系統的定位資訊瞭解到外部系統位置時

封閉分類法而非自由標籤——防止標籤膨脹導致召回時的模糊匹配。

feedback 型別有個細節：不只記錄糾正，也記錄使用者的肯定。原因很實際：只記錄"錯誤"會讓模型避免重蹈覆轍，但也可能無意間放棄使用者已經驗證過的好做法。這兩種型別還要求正文包含 Why 和 How to apply——因為知道"為什麼"才能判斷邊界情況，盲目執行規則往往適得其反。

project 型別有個具體要求：相對日期必須轉為絕對日期。"週四之後合併凍結"→"2026-03-05 後合併凍結"。記憶可能在幾周後被讀取，"週四"到時已毫無意義。

MEMORY.md 是索引不是容器。 它每次會話都完整載入到 system prompt，所以必須緊湊——每條一行連結，實際內容按需讀取。設有 200 行/25KB 雙重截斷，超出時追加提示"keep index entries to one line under ~200 chars"。錯誤訊息包含修復指引，這是貫穿整個系統的設計習慣。

召回機制用 sideQuery 調模型做語義匹配，而非關鍵詞搜尋。使用者問"部署流程"時，語義匹配能找到標題為"CI/CD 注意事項"的記憶，關鍵詞匹配則不行。召回在模型開始生成響應的同時非同步執行（pendingMemoryPrefetch），對使用者而言延遲近乎為零。每次最多返回 5 條，上下文成本可控。

每條記憶還附帶 freshness warning——超過 1 天的記憶會標註過期天數，提醒模型記憶是時間切片而非實時狀態。"下週截止"的記憶在兩週後讀到時，模型需要知道它可能已經過時。

TypeScript

// frontmatter.ts

export function parseFrontmatter(content: string): FrontmatterResult {
  const lines = content.split("\n");
  if (lines[0]?.trim() !== "---") return { meta: {}, body: content };

  let endIdx = -1;
  for (let i = 1; i < lines.length; i++) {
    if (lines[i].trim() === "---") { endIdx = i; break; }
  }
  if (endIdx === -1) return { meta: {}, body: content };

  const meta: Record<string, string> = {};
  for (let i = 1; i < endIdx; i++) {
    const colonIdx = lines[i].indexOf(":");
    if (colonIdx === -1) continue;
    const key = lines[i].slice(0, colonIdx).trim();
    const value = lines[i].slice(colonIdx + 1).trim();
    if (key) meta[key] = value;
  }

  const body = lines.slice(endIdx + 1).join("\n").trim();
  return { meta, body };
}

    if not lines or lines[0].strip() != "---":
        return FrontmatterResult(body=content)

    end_idx = -1

        if lines[i].strip() == "---":

        value = lines[i][colon_idx + 1:].strip()

語義召回（sideQuery）

早期版本用關鍵詞匹配做記憶召回——把查詢拆成詞，統計每條記憶的命中數排序。這很簡單但能力有限：使用者問"部署流程"時，標題為"CI/CD 注意事項"的記憶完全匹配不上，因為沒有共同關鍵詞。

新版本用 sideQuery 做語義召回：把所有記憶的檔名和描述發給模型，讓模型判斷哪些與當前查詢相關。

// memory.ts — selectRelevantMemories

const SELECT_MEMORIES_PROMPT = `You are selecting memories that will be useful to an AI coding assistant as it processes a user's query. You will be given the user's query and a list of available memory files with their filenames and descriptions.

Return a JSON object with a "selected_memories" array of filenames for the memories that will clearly be useful (up to 5). Only include memories that you are certain will be helpful based on their name and description.
- If you are unsure if a memory will be useful, do not include it.
- If no memories would clearly be useful, return an empty array.`;

export async function selectRelevantMemories(
  query: string,
  sideQuery: SideQueryFn,
  alreadySurfaced: Set<string>,
  signal?: AbortSignal,
): Promise<RelevantMemory[]> {
  const headers = scanMemoryHeaders();
  if (headers.length === 0) return [];

  // 過濾已經在本會話中展示過的記憶
  const candidates = headers.filter((h) => !alreadySurfaced.has(h.filePath));
  if (candidates.length === 0) return [];

  const manifest = formatMemoryManifest(candidates);

  try {
    const text = await sideQuery(
      SELECT_MEMORIES_PROMPT,
      `Query: ${query}\n\nAvailable memories:\n${manifest}`,
      signal,
    );

    // 從響應中提取 JSON（模型可能用 markdown 程式碼塊包裹）
    const jsonMatch = text.match(/\{[\s\S]*\}/);
    if (!jsonMatch) return [];

    const parsed = JSON.parse(jsonMatch[0]);
    const selectedFilenames: string[] = parsed.selected_memories || [];

    // 檔名對映回 header，讀取完整內容
    const filenameSet = new Set(selectedFilenames);
    const selected = candidates.filter((h) => filenameSet.has(h.filename));

    return selected.slice(0, 5).map((h) => {
      let content = readFileSync(h.filePath, "utf-8");
      // 單檔案截斷（4KB）
      if (Buffer.byteLength(content) > MAX_MEMORY_BYTES_PER_FILE) {
        content = content.slice(0, MAX_MEMORY_BYTES_PER_FILE) +
          "\n\n[... truncated, memory file too large ...]";
      }
      const freshness = memoryFreshnessWarning(h.mtimeMs);
      const headerText = freshness
        ? `${freshness}\n\nMemory: ${h.filePath}:`
        : `Memory (saved ${memoryAge(h.mtimeMs)}): ${h.filePath}:`;

      return { path: h.filePath, content, mtimeMs: h.mtimeMs, header: headerText };
    });
  } catch (err: any) {
    // 靜默失敗——記憶召回永遠不應阻塞主迴圈
    if (signal?.aborted) return [];
    console.error(`[memory] semantic recall failed: ${err.message}`);
    return [];
  }
}

幾個關鍵設計點：

sideQuery 用的是同一個模型，不是單獨的小模型。 Claude Code 用 Sonnet 做 sideQuery，我們簡化為直接複用使用者配置的模型。sideQuery 只傳送記憶清單（檔名 + 描述），不傳送完整內容，所以輸入 token 很少。

模型做語義選擇，比關鍵詞匹配強得多。 "部署流程"能匹配到"CI/CD 注意事項"，"資料庫效能"能匹配到"PostgreSQL 索引最佳化經驗"——因為模型理解語義關聯，不只是字面重疊。

alreadySurfaced Set 防止重複召回。 同一會話中已經展示過的記憶不會再次出現，避免使用者每次提問都看到相同的記憶。這個 Set 在整個會話生命週期內持續增長。

單檔案 4KB 截斷 + 會話總預算 60KB。 防止單條巨大記憶或累積過多召回擠佔上下文。預算是位元組級控制，不是 token 級——位元組計算更快，且對多語言文字更公平。

對比舊版關鍵詞匹配（已替換）： 舊實現把查詢拆詞後逐條匹配，零 API 呼叫但準確度低。新版每次召回消耗 1 次 API 呼叫，但語義理解能力質的飛躍。對於教程專案記憶量少的場景，這個 API 成本完全可以接受。

非同步預取（startMemoryPrefetch）

語義召回需要一次 API 呼叫，如果同步執行會增加使用者等待時間。解決方案：在使用者提交輸入的瞬間就啟動召回，與第一次模型 API 呼叫並行執行。

// memory.ts — startMemoryPrefetch

export function startMemoryPrefetch(
  query: string,
  sideQuery: SideQueryFn,
  alreadySurfaced: Set<string>,
  sessionMemoryBytes: number,
  signal?: AbortSignal,
): MemoryPrefetch | null {
  // 門控 1: 單詞查詢跳過（太短，無法語義匹配）
  if (!/\s/.test(query.trim())) return null;

  // 門控 2: 會話預算已滿
  if (sessionMemoryBytes >= MAX_SESSION_MEMORY_BYTES) return null;

  // 門控 3: 沒有記憶檔案
  const dir = getMemoryDir();
  const hasMemories = readdirSync(dir).some(
    (f) => f.endsWith(".md") && f !== "MEMORY.md"
  );
  if (!hasMemories) return null;

  const handle: MemoryPrefetch = {
    promise: selectRelevantMemories(query, sideQuery, alreadySurfaced, signal),
    settled: false,
    consumed: false,
  };
  handle.promise.then(() => { handle.settled = true; }).catch(() => { handle.settled = true; });
  return handle;
}

這個設計的關鍵在於非阻塞輪詢：

  1. 預取在使用者輸入時啟動——與第一次模型 API 呼叫並行，使用者感知不到額外延遲
  1. 每次迴圈迭代都檢查——如果預取還沒完成，不等待，直接跳過；下一次迭代再檢查
  1. settled 標誌用 .then() 設定——不用 await，只在確認完成後才讀取結果
  1. 消費後標記 consumed = true——確保同一次預取只注入一次

三個門控條件避免浪費 API 呼叫：

  • 多詞查詢：單個詞（如 "hi"）太短，語義匹配無意義
  • 會話預算：累積超過 60KB 後停止召回，防止上下文過載
  • 記憶存在性：沒有記憶檔案時跳過，省一次 API 呼叫

Freshness Warning

記憶是時間切片，不是實時狀態。一條"專案下週截止"的記憶在兩週後讀到時已經過時，模型如果不知道這一點就會給出錯誤建議。

// memory.ts — memoryFreshnessWarning

export function memoryFreshnessWarning(mtimeMs: number): string {
  const days = Math.max(0, Math.floor((Date.now() - mtimeMs) / 86_400_000));
  if (days <= 1) return "";
  return `This memory is ${days} days old. Memories are point-in-time observations, not live state — claims about code behavior may be outdated. Verify against current code before asserting as fact.`;
}

規則很簡單：1 天以內不提示（資訊基本新鮮），超過 1 天就附帶警告。警告文字明確告訴模型兩件事："這是過去某個時刻的觀察"和"需要對照當前程式碼驗證"。這比簡單標註"X 天前"更有效——它給出了行動指引，而非只是資訊。

關鍵設計決策

為什麼記憶用檔案系統而非資料庫？ 三個好處：使用者可以直接用編輯器讀寫記憶檔案；模型用已有的 write_file/read_file 工具就能操作，不需要專門的記憶 API；如有需要可以納入 git 版本控制。記憶系統"寄生"在工具系統上，減少了需要暴露的介面數量。

為什麼用語義召回而非關鍵詞匹配？ 關鍵詞匹配只能找到字面重疊的記憶，語義召回能理解"部署流程"和"CI/CD 注意事項"的關聯。代價是每次召回消耗 1 次 API 呼叫，但 sideQuery 只傳送記憶清單（檔名 + 描述），輸入 token 極少，成本很低。對於記憶量有限的場景，這個 trade-off 完全值得。

為什麼非同步預取而非同步召回？ 同步召回意味著使用者每次提問都要多等一個 API 往返。預取與第一次模型呼叫並行，如果預取先完成，記憶在第一輪響應中就可見；如果沒完成，第二輪也能趕上。最差情況下記憶晚到一輪，但使用者永遠不需要等。

為什麼需要會話級預算？ 無限召回會讓上下文充滿記憶，擠掉真正的對話內容。60KB 預算大約相當於 20-30 條中等長度的記憶，足夠覆蓋一次會話的上下文需求。alreadySurfaced 集合配合預算上限，讓越到會話後期記憶召回越精準——已經展示過的不重複，預算內只留真正需要的。

Claude Code 怎麼做的

技能是 Claude Code 的"AI Shell 指令碼"——把 AI 工作流模板化，一次定義，反覆複用。一個 /commit 技能封裝了"讀 diff → 分析變更 → 撰寫 commit message → 提交"的完整 prompt。

技能從 6 個來源載入，優先順序從高到低：企業策略（managed）> 專案級 > 使用者級 > 外掛 > 內建（bundled）> MCP。規律很簡單：越接近使用者控制的來源優先順序越高，MCP 來自遠端不受信任的服務端所以墊底。每個技能必須是目錄格式 skill-name/SKILL.md，允許技能附帶資原始檔並透過 ${CLAUDE_SKILL_DIR} 引用。

啟動時只預載入 frontmatter（name/description/whenToUse），完整 prompt 在呼叫時才讀取。幾十個技能全量載入會擠佔大量上下文，懶載入把成本推遲到真正需要的時刻。即使只是 frontmatter，技能列表也需要 token 空間——formatCommandsWithinBudget() 用三階段演算法控制：預算充足時全量展示；超出時內建技能（/commit、/review）始終保留完整描述，其餘按剩餘預算均分；每個技能不足 20 字元時降級為僅顯示名稱。

技能 prompt 執行前經過多層替換：$ARGUMENTS 替換使用者引數，${CLAUDE_SKILL_DIR} 替換技能目錄路徑，` !command ` 內聯 Shell 執行（MCP 技能禁用此特性，防止遠端提示詞注入執行任意命令）。

執行模式有兩種：inline（預設）直接注入當前對話，fork 建立獨立子 Agent 執行後返回結果。fork 適合需要大量工具呼叫的技能——比如程式碼審查要讀多個檔案，這些呼叫會汙染主對話上下文，fork 後只有最終結果回到主線。

function parseSkillFile(
  filePath: string, source: "project" | "user", skillDir: string
): SkillDefinition | null {
  const raw = readFileSync(filePath, "utf-8");
  const { meta, body } = parseFrontmatter(raw);

  const name = meta.name || skillDir.split("/").pop() || "unknown";
  const userInvocable = meta["user-invocable"] !== "false";

  let allowedTools: string[] | undefined;
  if (meta["allowed-tools"]) {
    const raw = meta["allowed-tools"];
    if (raw.startsWith("[")) {
      try { allowedTools = JSON.parse(raw); } catch {
        allowedTools = raw.replace(/[\[\]]/g, "").split(",").map((s) => s.trim());
      }
    } else {
      allowedTools = raw.split(",").map((s) => s.trim());
    }
  }

  return {
    name, description: meta.description || "",
    whenToUse: meta.when_to_use || meta["when-to-use"],
    allowedTools, userInvocable,
    promptTemplate: body, source, skillDir,
  };
}

// agent.ts — executeSkillTool

private async executeSkillTool(input: Record<string, any>): Promise<string> {
  const result = executeSkill(input.skill_name, input.args || "");
  if (!result) return `Unknown skill: ${input.skill_name}`;

  if (result.context === "fork") {
    const tools = result.allowedTools
      ? this.tools.filter(t => result.allowedTools!.includes(t.name))
      : this.tools.filter(t => t.name !== "agent");
    const subAgent = new Agent({
      customSystemPrompt: result.prompt,
      customTools: tools,
      isSubAgent: true,
      permissionMode: "bypassPermissions",
    });
    const subResult = await subAgent.runOnce(input.args || "Execute this skill task.");
    return subResult.text;
  }

  return `[Skill "${input.skill_name}" activated]\n\n${result.prompt}`;
}

關鍵設計決策

為什麼技能用 Markdown 而非 JSON/YAML？ 技能的本體是大段自然語言 prompt。Markdown 的 body 直接就是 prompt 本身，frontmatter 提供結構化後設資料。JSON 儲存的話 prompt 需要轉義換行符和引號，可讀性很差。

為什麼需要雙重呼叫路徑？ 只支援 /commit 手動呼叫不夠——使用者可能說"幫我提交程式碼"而不知道有這個技能；只支援模型自動呼叫也不夠——使用者有時想精確控制觸發時機。兩條路徑最終匯合到同一個 resolveSkillPrompt()，邏輯不重複。

Claude Code 怎麼做的

Claude Code 的 Plan Mode 是完整的 EnterPlanMode / ExitPlanMode 工具對：

  1. 進入：切換到 read-only 模式，生成 plan 檔案（~/.claude/plans/ 目錄），注入 plan 系統提示約束 Agent 行為
  1. 規劃：Agent 用只讀工具探索程式碼，將實現計劃寫入 plan 檔案
  1. 退出：Agent 呼叫 ExitPlanMode，使用者看到計劃後選擇執行方式
  1. 審批：使用者選擇清空上下文執行、保留上下文執行、手動審批執行、或繼續修改

關鍵設計：Plan Mode 不是"不讓 Agent 做事"，而是讓 Agent 先想清楚再做。plan 檔案持久化到磁碟意味著即使清空上下文，計劃也不會丟失——Agent 可以從零開始執行一個經過審批的方案。

// agent.ts — executePlanModeTool()

private async executePlanModeTool(name: string): Promise<string> {
  if (name === "enter_plan_mode") {
    if (this.permissionMode === "plan") {
      return "Already in plan mode.";
    }
    this.prePlanMode = this.permissionMode;
    this.permissionMode = "plan";
    this.planFilePath = this.generatePlanFilePath();
    this.systemPrompt = this.baseSystemPrompt + this.buildPlanModePrompt();
    if (this.useOpenAI && this.openaiMessages.length > 0) {
      (this.openaiMessages[0] as any).content = this.systemPrompt;
    }
    printInfo("Entered plan mode (read-only). Plan file: " + this.planFilePath);
    return `Entered plan mode. You are now in read-only mode.\n\n` +
      `Your plan file: ${this.planFilePath}\n` +
      `Write your plan to this file. This is the only file you can edit.\n\n` +
      `When your plan is complete, call exit_plan_mode.`;
  }

  if (name === "exit_plan_mode") {
    if (this.permissionMode !== "plan") {
      return "Not in plan mode.";
    }
    // 讀取 plan 檔案內容
    let planContent = "(No plan file found)";
    if (this.planFilePath && existsSync(this.planFilePath)) {
      planContent = readFileSync(this.planFilePath, "utf-8");
    }

    // 互動式審批流程
    if (this.planApprovalFn) {
      const result = await this.planApprovalFn(planContent);

      if (result.choice === "keep-planning") {
        // 使用者拒絕 — 留在 plan 模式，返回反饋給模型
        const feedback = result.feedback || "Please revise the plan.";
        return `User rejected the plan and wants to keep planning.\n\n` +
          `User feedback: ${feedback}\n\n` +
          `Please revise your plan based on this feedback. When done, call exit_plan_mode again.`;
      }

      // 使用者批准 — 確定目標許可權模式
      let targetMode: PermissionMode;
      if (result.choice === "clear-and-execute" || result.choice === "execute") {
        targetMode = "acceptEdits";
      } else {
        targetMode = this.prePlanMode || "default";  // manual-execute: 恢復原模式
      }

      // 退出 plan 模式
      this.permissionMode = targetMode;
      this.prePlanMode = null;
      const savedPlanPath = this.planFilePath;
      this.planFilePath = null;
      this.systemPrompt = this.baseSystemPrompt;

      // 清空上下文（如果選擇了 clear-and-execute）
      if (result.choice === "clear-and-execute") {
        this.clearHistoryKeepSystem();
        this.contextCleared = true;
        printInfo(`Plan approved. Context cleared, executing in ${targetMode} mode.`);
        return `User approved the plan. Context was cleared. Permission mode: ${targetMode}\n\n` +
          `Plan file: ${savedPlanPath}\n\n## Approved Plan:\n${planContent}\n\nProceed with implementation.`;
      }

      printInfo(`Plan approved. Executing in ${targetMode} mode.`);
      return `User approved the plan. Permission mode: ${targetMode}\n\n` +
        `## Approved Plan:\n${planContent}\n\nProceed with implementation.`;
    }

    // Fallback: 沒有審批函式時直接退出（如子 Agent）
    this.permissionMode = this.prePlanMode || "default";
    this.prePlanMode = null;
    this.planFilePath = null;
    this.systemPrompt = this.baseSystemPrompt;
    printInfo("Exited plan mode. Restored to " + this.permissionMode + " mode.");
    return `Exited plan mode. Permission mode restored to: ${this.permissionMode}\n\n` +
      `## Your Plan:\n${planContent}`;
  }

  return `Unknown plan mode tool: ${name}`;
}

設計決策

為什麼 Plan 檔案寫磁碟？

Plan 檔案持久化到 ~/.claude/plans/ 有兩個原因：

  1. Clear-and-execute 選項需要：清空上下文後，對話歷史中的 plan 內容會丟失。但 plan 檔案在磁碟上，Agent 可以重新讀取。
  1. 跨會話可用：使用者可以 --resume 恢復會話時看到之前的 plan，或者手動檢視歷史 plan 檔案。

為什麼審批是回撥而不是直接實現？

planApprovalFn 是外部注入的回撥，而不是 Agent 內部直接實現。這讓 Agent 類不依賴具體的 UI 實現——CLI 用 readline，IDE 整合可以用 GUI 對話方塊，測試時可以注入模擬函式。子 Agent 沒有審批函式時直接退出，不需要特殊處理。

為什麼 clear-and-execute 切換到 acceptEdits？

使用者既然審批了計劃並選擇了自動執行，說明他們信任 Agent 的修改方向。切換到 acceptEdits 讓 Agent 無需反覆確認每次檔案編輯，大幅提升執行效率。如果使用者想逐步審批，有專門的選項 3。

Claude Code 怎麼做的

Claude Code 的多 Agent 體系在 src/tools/AgentTool/ 中實現，支援三種協作模式：

模式特點
------------
**Sub-Agent**（fork-return）分叉獨立執行，完成後返回結果
**Coordinator**一個協調者分配任務給多個 Worker
**Swarm Team**多 Agent 對等協作，透過信箱通訊

我們實現的是 Sub-Agent 模式，也是最常用的。

內建 Agent 型別

  • Explore：用 Haiku 模型（更便宜），只讀工具集，專門用於程式碼搜尋
  • Plan：只讀 + 結構化輸出，設計實現方案
  • General：完整工具集（除了不能遞迴建立子 Agent）
  • Custom：透過 .claude/agents/*.md 檔案定義

Coordinator 模式的關鍵設計

Coordinator 將主 Agent 變為純編排者——工具集被硬限制為只有 Agent（派生 Worker）和 SendMessage（續傳 Worker），完全無法執行檔案操作。這個硬約束防止協調器"懶得委託、自己動手"而退化成普通單 Agent。

標準工作流分四階段：研究（並行只讀）→ 綜合（協調器序列理解）→ 實施（按檔案集序列）→ 驗證。

其中綜合階段有個反直覺的約束：提示詞裡明確禁止寫 "based on your findings"。這強制協調器真正理解並具體化研究結果（包含檔案路徑、行號），而不是把理解工作轉包給下一個 Worker。

每個 Worker 都是從零開始的獨立 Agent，看不到協調器與使用者的對話，所以協調器寫給 Worker 的 prompt 必須自包含——這是 Coordinator 模式中最容易踩坑的地方。

工具過濾：4 層管道

子 Agent 的工具訪問經過 4 層過濾，實現縱深防禦：

  1. 移除元工具（TaskOutput、EnterPlanMode、AskUserQuestion 等）——子 Agent 不應控制 Agent 執行流程
  1. 對自定義 Agent 額外限制——使用者定義的型別不與內建型別同級信任
  1. 非同步 Agent 用白名單模式——後臺執行無法展示互動 UI，必須嚴格限制
  1. Agent 型別級 disallowedTools——如 Explore 顯式排除寫入工具

前三層是全域性策略，第四層是型別策略。即使自定義 Agent 設定了 disallowedTools: []，前三層仍然有效。

上下文隔離

子 Agent 採用 deny-by-default：訊息歷史完全獨立，abortController 單向傳播（父中斷→子中斷，反之不行），子 Agent 的狀態變更預設不傳播到父級 UI。只有一個例外：Bash 啟動的後臺程序必須註冊到根 store，否則成為殭屍程序。

Worktree 隔離

多 Agent 並行寫檔案時，Claude Code 給每個寫操作 Agent 分配獨立的 Git Worktree——共享 .git 目錄但有獨立工作目錄，完全無衝突，開銷比 git clone 小得多。

async runOnce(prompt: string): Promise<{ text: string; tokens: { input: number; output: number } }> {
  this.outputBuffer = [];
  const prevInput = this.totalInputTokens;
  const prevOutput = this.totalOutputTokens;
  await this.chat(prompt);                         // 複用完整 agent loop
  const text = this.outputBuffer.join("");
  this.outputBuffer = null;
  return {
    text,
    tokens: {
      input: this.totalInputTokens - prevInput,
      output: this.totalOutputTokens - prevOutput,
    },
  };
}

子 Agent 出錯時返回錯誤字串，不會讓父 Agent 崩潰——父 Agent 的 LLM 看到錯誤資訊後可以自行決定重試或換策略。

許可權繼承：子 Agent 預設 bypassPermissions（主 Agent 已授權，子 Agent 不必再詢問使用者），但 Plan Mode 必須繼承——否則子 Agent 可以繞過只讀限制，是個安全漏洞。

關鍵設計決策

Fork-return 為什麼比 Coordinator 更適合作為起點？

Fork-return 的優勢很簡單：無共享狀態（不可能汙染主 Agent 上下文）、控制流確定（發請求等結果）、容錯簡單（子 Agent 出錯主 Agent 繼續工作）。Coordinator 在任務並行化上更強，但需要處理 Worker 之間的資訊共享、衝突，複雜度高一個數量級。

為什麼子 Agent 不能建立子 Agent？

General Agent 工具列表裡過濾掉了 agent。不限制的話，A 建立 B、B 建立 C 的遞迴巢狀會指數級消耗 token——每層都有自己的系統提示詞和訊息歷史。Claude Code 做了同樣的限制，實踐中 1 層已覆蓋絕大多數場景。

為什麼 explore/plan 保留 run_shell？

git log --oneline -20、find . -name "*.ts" | wc -l 這類只讀 shell 命令是程式碼探索的核心手段，完全禁止會大幅削弱能力。這個設計與 Claude Code 的 Explore Agent 一致——用 system prompt 約束而非徹底禁用工具。

為什麼用 buffer 收集輸出而不是回撥？

回撥方案需要把 onText 傳入建構函式，然後在 agent loop 裡到處判斷。Buffer 方案只改 emitText 一處，runOnce 開啟、chat 寫入、runOnce 收集並關閉，生命週期邊界清晰，對現有程式碼零侵入。

整個實現的核心洞察：子 Agent 本質上就是一個配置不同的 Agent 例項。透過給 Agent 類新增少量可選引數（customTools、customSystemPrompt、isSubAgent），同一套 agent loop 同時服務於主 Agent 和子 Agent，避免了程式碼重複。

核心思路：spawn 子程序 → JSON-RPC 握手 → 發現工具 → 字首註冊 → 透明路由。對 Agent Loop 來說，MCP 工具和內建工具沒有區別——都是名字 + schema + 執行函式。

Claude Code 怎麼做的

MCP（Model Context Protocol）是 Anthropic 釋出的開放協議，用於連線 AI 助手與外部工具。Claude Code 的 MCP 實現有以下要點：

配置發現：從 settings.json（使用者級、專案級）和 .mcp.json（專案根目錄）三處讀取伺服器配置，優先順序後讀覆蓋先讀。企業級還支援 MDM 策略下發。

傳輸協議：支援 stdio（子程序通訊）和 SSE（HTTP 長連線）兩種傳輸方式。stdio 是主流，SSE 用於遠端服務。

工具命名：所有 MCP 工具以 mcp__serverName__toolName 格式註冊，三段式命名同時解決了命名衝突和路由問題——從名字就能知道該轉發到哪個伺服器。

連線生命週期：spawn 程序 → initialize 握手（交換版本和能力）→ notifications/initialized 確認 → tools/list 發現工具 → 就緒。初始化和工具發現各有 15 秒超時。

動態重新整理：Claude Code 支援執行時重新發現工具（伺服器可以通知客戶端工具列表已變更），我們簡化為一次性發現。

SDK 依賴：Claude Code 使用 @anthropic-ai/sdk 內建的 MCP 客戶端，封裝了 JSON-RPC 細節。我們直接實現原始 JSON-RPC，不依賴任何 MCP SDK。

關鍵程式碼

1. MCP 連線 — McpConnection 類

每個 MCP 伺服器對應一個 McpConnection 例項，負責子程序管理和 JSON-RPC 通訊。

class McpConnection {
  private process: ChildProcess | null = null;
  private nextId = 1;
  private pending = new Map<number, { resolve: (v: any) => void; reject: (e: Error) => void }>();
  private rl: Interface | null = null;

  constructor(private serverName: string, private config: McpServerConfig) {}

三個關鍵狀態：process 是子程序控制代碼，pending 是請求-響應關聯表（id → Promise），rl 是 readline 例項用於按行解析 JSON-RPC。

連線與訊息解析

  async connect(): Promise<void> {
    const env = { ...process.env, ...(this.config.env || {}) };
    this.process = spawn(this.config.command, this.config.args || [], {
      stdio: ["pipe", "pipe", "pipe"],
      env,
    });

    // 按行解析 stdout 中的 JSON-RPC 訊息
    this.rl = createInterface({ input: this.process.stdout! });
    this.rl.on("line", (line: string) => {
      try {
        const msg = JSON.parse(line);
        if (msg.id !== undefined && this.pending.has(msg.id)) {
          const { resolve, reject } = this.pending.get(msg.id)!;
          this.pending.delete(msg.id);
          if (msg.error) {
            reject(new Error(`MCP error ${msg.error.code}: ${msg.error.message}`));
          } else {
            resolve(msg.result);
          }
        }
      } catch {
        // 忽略非 JSON 行（伺服器日誌等）
      }
    });
  }

stdio 模式的核心：子程序的 stdin/stdout 作為雙向通訊通道，每行一個 JSON-RPC 訊息。pending Map 用自增 id 關聯請求和響應——傳送時存入 Promise，收到響應時 resolve 或 reject。

請求與通知

JSON-RPC 有兩種訊息：請求（有 id，期望響應）和通知（無 id，發後不管）。

  /** 傳送請求，等待響應 */
  private sendRequest(method: string, params: any = {}): Promise<any> {
    return new Promise((resolve, reject) => {
      if (!this.process?.stdin?.writable) {
        return reject(new Error(`MCP server '${this.serverName}' is not connected`));
      }
      const id = this.nextId++;
      this.pending.set(id, { resolve, reject });
      const msg = JSON.stringify({ jsonrpc: "2.0", id, method, params }) + "\n";
      this.process.stdin.write(msg);
    });
  }

  /** 傳送通知，不等響應 */
  private sendNotification(method: string, params: any = {}): void {
    if (!this.process?.stdin?.writable) return;
    const msg = JSON.stringify({ jsonrpc: "2.0", method, params }) + "\n";
    this.process.stdin.write(msg);
  }

區別只在有無 id 欄位。有 id 的訊息寫入 pending 等待配對；無 id 的直接寫入 stdin 就結束。

握手、發現、呼叫

  /** MCP 初始化握手 */
  async initialize(): Promise<void> {
    await this.sendRequest("initialize", {
      protocolVersion: "2024-11-05",
      capabilities: {},
      clientInfo: { name: "mini-claude", version: "1.0.0" },
    });
    // 握手成功後發通知確認
    this.sendNotification("notifications/initialized");
  }

  /** 發現伺服器提供的工具 */
  async listTools(): Promise<McpToolInfo[]> {
    const result = await this.sendRequest("tools/list");
    if (!result?.tools || !Array.isArray(result.tools)) return [];
    return result.tools.map((t: any) => ({
      name: t.name,
      description: t.description || "",
      inputSchema: t.inputSchema,
      serverName: this.serverName,
    }));
  }

  /** 呼叫工具，返回文字結果 */
  async callTool(name: string, args: any): Promise<string> {
    const result = await this.sendRequest("tools/call", { name, arguments: args });
    if (result?.content && Array.isArray(result.content)) {
      return result.content
        .filter((c: any) => c.type === "text")
        .map((c: any) => c.text)
        .join("\n");
    }
    return JSON.stringify(result);
  }

三步標準流程：initialize（版本協商）→ listTools（工具發現）→ callTool（執行呼叫）。MCP 協議要求 initialize 之後必須發 notifications/initialized 通知，告訴伺服器客戶端準備就緒。

callTool 的返回值處理值得注意：MCP 返回 { content: [{ type: "text", text: "..." }] } 格式，我們只提取 text 型別的內容拼接返回——圖片等其他型別暫不處理。

2. MCP 管理器 — McpManager 類

配置載入

export class McpManager {
  private connections = new Map<string, McpConnection>();
  private tools: McpToolInfo[] = [];
  private connected = false;

  private loadConfigs(): Record<string, McpServerConfig> {
    const merged: Record<string, McpServerConfig> = {};

    // 1. 使用者級：~/.claude/settings.json
    const globalPath = join(homedir(), ".claude", "settings.json");
    this.mergeConfigFile(globalPath, merged);

    // 2. 專案級：.claude/settings.json
    const projectPath = join(process.cwd(), ".claude", "settings.json");
    this.mergeConfigFile(projectPath, merged);

    // 3. MCP 專用：.mcp.json
    const mcpJsonPath = join(process.cwd(), ".mcp.json");
    this.mergeConfigFile(mcpJsonPath, merged);

    return merged;
  }

  private mergeConfigFile(filePath: string, target: Record<string, McpServerConfig>): void {
    if (!existsSync(filePath)) return;
    try {
      const raw = JSON.parse(readFileSync(filePath, "utf-8"));
      const servers = raw.mcpServers || raw;  // .mcp.json 可能直接是伺服器對映
      for (const [name, config] of Object.entries(servers)) {
        if (this.isValidConfig(config)) {
          target[name] = config as McpServerConfig;
        }
      }
    } catch {
      // 靜默跳過格式錯誤的配置檔案
    }
  }

三處配置依次讀取、合併，同名伺服器後讀覆蓋先讀。raw.mcpServers || raw 這行相容兩種格式：settings.json 的 mcpServers 巢狀結構和 .mcp.json 的扁平結構。

連線與發現

  async loadAndConnect(): Promise<void> {
    if (this.connected) return;  // 冪等：多次呼叫只連一次
    this.connected = true;

    const configs = this.loadConfigs();
    if (Object.keys(configs).length === 0) return;

    const TIMEOUT_MS = 15_000;

    for (const [name, config] of Object.entries(configs)) {
      const conn = new McpConnection(name, config);
      try {
        await conn.connect();
        // 握手和工具發現都有 15 秒超時
        await Promise.race([
          conn.initialize(),
          new Promise((_, rej) => setTimeout(() => rej(new Error("timeout")), TIMEOUT_MS)),
        ]);
        const serverTools = await Promise.race([
          conn.listTools(),
          new Promise<McpToolInfo[]>((_, rej) => setTimeout(() => rej(new Error("timeout")), TIMEOUT_MS)),
        ]);
        this.connections.set(name, conn);
        this.tools.push(...serverTools);
        console.error(`[mcp] Connected to '${name}' — ${serverTools.length} tools`);
      } catch (err: any) {
        console.error(`[mcp] Failed to connect to '${name}': ${err.message}`);
        conn.close();  // 失敗的連線立即清理，不影響其他伺服器
      }
    }
  }

Promise.race 配合 setTimeout 實現超時。為什麼是 15 秒？MCP 伺服器常用 npx 啟動，首次執行需要下載包，但也不應該無限等待。每個伺服器獨立連線，一個失敗不影響其他。

工具定義轉換

  getToolDefinitions(): Array<{ name: string; description: string; input_schema: any }> {
    return this.tools.map((t) => ({
      name: `mcp__${t.serverName}__${t.name}`,
      description: t.description || `MCP tool ${t.name} from ${t.serverName}`,
      input_schema: t.inputSchema || { type: "object", properties: {} },
    }));
  }

關鍵操作：把 MCP 原始工具名轉換成三段式字首名。filesystem 伺服器的 read_file 工具變成 mcp__filesystem__read_file。返回的格式直接符合 Anthropic API 的 tool 定義規範，可以直接拼接到工具列表裡。

路由與呼叫

  isMcpTool(name: string): boolean {
    return name.startsWith("mcp__");
  }

  async callTool(prefixedName: string, args: any): Promise<string> {
    // mcp__serverName__toolName → serverName, toolName
    const parts = prefixedName.split("__");
    if (parts.length < 3) throw new Error(`Invalid MCP tool name: ${prefixedName}`);
    const serverName = parts[1];
    const toolName = parts.slice(2).join("__");  // 工具名可能包含 __
    const conn = this.connections.get(serverName);
    if (!conn) throw new Error(`MCP server '${serverName}' not connected`);
    return conn.callTool(toolName, args);
  }

路由邏輯非常簡潔：從字首名中拆出伺服器名和工具名，找到對應連線，轉發呼叫。parts.slice(2).join("__") 處理工具名本身可能包含 __ 的情況（雖然罕見，但協議不禁止）。

// agent.ts — executeToolCall() 方法

關鍵設計決策

為什麼用 JSON-RPC over stdio 而不是 HTTP？

stdio 的優勢是零配置：不需要埠管理、不需要發現服務、程序生命週期自動繫結到父程序。子程序退出時所有 pending 請求自動 reject，不存在連線洩漏。HTTP 方案需要處理埠衝突、程序發現、心跳檢測，複雜度高一個數量級。

為什麼用三段式字首名（mcp__server__tool）？

一個名字同時解決兩個問題：避免衝突（不同伺服器可能有同名工具）和嵌入路由資訊（從名字直接提取伺服器名，無需額外對映表）。Claude Code 用完全相同的命名方案。

為什麼 15 秒超時？

MCP 伺服器常用 npx 啟動，首次執行需要下載 npm 包，通常需要 3-8 秒。15 秒足夠覆蓋大多數情況，但不至於讓使用者等太久。超時後靜默跳過該伺服器，Agent 繼續用其他可用工具工作。

為什麼懶連線（首次 chat 時而非啟動時）？

使用者可能啟動 Agent 只是想問一句"這個函式是什麼意思"，根本用不到 MCP 工具。懶連線讓這種場景零開銷。代價是第一次需要 MCP 工具時會有幾秒延遲，但只發生一次。

為什麼不用 MCP SDK？

@anthropic-ai/sdk 提供了 MCP 客戶端封裝，但直接用原始 JSON-RPC 有兩個好處：零依賴（不增加包體積）和教學價值（讀者能看到協議的完整細節，理解 MCP 到底在做什麼）。整個 JSON-RPC 通訊只有 ~60 行程式碼，足夠簡單。

我們沒實現的

Hooks（鉤子系統）

Claude Code 有 25 種 hook 事件、6 種 hook 型別，可在工具執行前後插入自定義邏輯——攔截危險操作、記錄審計日誌、自動執行 lint 檢查。它是 Claude Code 從"工具"變成"平臺"的關鍵機制。

我們沒實現的原因：核心挑戰不在於"調一個函式"，而在於 hook 的發現與載入、錯誤隔離、stdin/stdout JSON 資料協議。這些工程細節約 500-800 行，但對理解 agent 原理沒有幫助。

Coordinator / Swarm 多 Agent 模式

我們實現了 Sub-Agent（fork-return）。Claude Code 還有兩種模式：Coordinator 把大任務拆分給多個專業 Agent，Swarm 讓多個 Agent 對等通訊、並行探索。兩種模式解決的是單 Agent 上下文不夠時的任務分解問題。

沒實現的原因：核心挑戰是任務分解準確性和 Agent 間通訊協議設計，更多是 prompt engineering 問題而非程式碼架構問題。實現本身不復雜，但要真正好用需要大量 prompt 調優。

LSP 整合

LSP 讓 agent 在編輯檔案後毫秒級獲得型別錯誤反饋，而不需要等完整的編譯/測試周期。在大型專案中，這能把修復一個 bug 所需的迴圈次數減少 30-50%。

沒實現的原因：需要管理 LSP 伺服器程序、實現客戶端協議（初始化握手、能力協商、增量同步），1000+ 行且依賴對 LSP 協議的深入理解。透過 shell 命令（tsc --noEmit、python -m py_compile）獲得錯誤反饋，對教程場景已經足夠。

Prompt Caching

Anthropic API 支援快取系統提示詞——Claude Code 把不變的部分（角色定義、工具規範）放前面，變化的部分（git 狀態、當前檔案）放後面，快取命中可將輸入 token 成本降低 90%。

沒實現的原因：程式碼改動極小（20-30 行），但需要仔細設計提示詞分割槽策略。如果你的 agent 要上線，這應該是第一個加上的最佳化。

Bash AST 安全分析

Claude Code 用 tree-sitter 解析 shell 命令的 AST，進行 23 項靜態安全檢查，能分析出管道組合中的危險命令——這是純正則做不到的。

沒實現的原因：tree-sitter 是 C/C++ 原生庫，需要 node-gyp 編譯環境，環境障礙太高。正則匹配覆蓋了 80% 的常見危險模式，教程場景風險可接受。

擴充套件方向

1. Hooks 系統

最簡單的方案是 command hook——在 executeTool 前 spawn shell 子程序，透過 stdin JSON 傳入工具資訊，解析 stdout JSON 決定 allow/deny。

配置示例：

{
  "hooks": {
    "PreToolUse": [
      { "matcher": "run_shell", "command": "./hooks/pre-shell.sh" }
    ]
  }
}

核心邏輯：遍歷匹配的 hook，spawn 子程序傳 JSON，根據 {"action": "allow"} / {"action": "deny", "reason": "..."} 決定是否繼續執行。約 300 行，最耗時的是子程序的超時和 crash 處理。

2. 錯誤自修復

把工具執行錯誤作為工具結果反饋給模型，而不是中斷迴圈。模型經常能自己修復：路徑拼錯換路徑、命令引數錯了改引數。

try {
  result = await executeToolImpl(name, input);
} catch (e) {
  result = `Error: ${e.message}\n\nPlease try a different approach.`;
}
// 把 result 作為 tool_result 返回給模型

約 50-80 行，但能顯著提升 agent 實際可用性——這是 Claude Code 最聰明的設計之一。

核心洞察

1. Agent 的本質是一個 while 迴圈

while true:
    response = llm.call(messages)
    if no tool_calls in response: break
    for tool_call in response.tool_calls:
        result = execute(tool_call)
        messages.append(result)

所有的複雜性——許可權、上下文管理、記憶、多 Agent——都是圍繞這個迴圈的增強和防護。

2. 提示詞是最便宜的程式碼

系統提示詞裡的一句話，效果等同於一個 if 語句，實現成本是 0 行程式碼。agent 開發中很多行為問題的最優解不是寫更多程式碼，而是寫更好的提示詞——更靈活、更容易修改、非技術人員也能讀懂。

3. 工具設計決定能力上限

讓模型做它擅長的（理解意圖、生成程式碼），讓工具做模型不擅長的（精確字串匹配、檔案系統操作、程序管理）。edit_file 是典型：模型生成要替換的內容，工具負責在檔案中精確定位和替換。

4. 上下文管理是 agent 的"記憶力"

上下文管理之於 agent，就像記憶體管理之於作業系統——用有限資源提供"無限"錯覺。4 層壓縮流水線讓 agent 在有限視窗中保持對長對話的記憶。

5. 安全不是事後補丁

許可權檢查是 agent 迴圈的一個步驟，不是外掛的 middleware。沒有任何工具可以繞過它。更重要的是 fail-closed 設計：新工具如果忘記宣告許可權級別，被自動當作"需要確認"處理——系統透過預設值保證安全。

6. 從 3000 行到 50 萬行的差距在於邊緣情況

Claude Code 多出來的程式碼大多是：各執行環境相容性、網路和 API 不可靠性、使用者輸入多樣性、企業級審計和訪問控制。這些"無聊"的程式碼不會出現在架構圖中，卻是工具能否在真實世界可靠執行的關鍵。從原型到產品，80% 的距離在這裡。

7. LLM 與程式碼的協作邊界

構建 coding agent 最核心的能力：設計好 LLM 和程式碼之間的協作邊界。哪些讓 LLM 決定，哪些讓程式碼決定——邊界劃得好，agent 既靈活又可靠。我們在教程裡每個設計決策都體現了這個原則：模型決定"做什麼"，程式碼確保"安全地做"。

為什麼需要手動測試

Coding Agent 的測試和普通軟體不同——核心行為取決於 LLM 的響應，輸出不確定。自動化單元測試能覆蓋工具函式（檔案讀寫、許可權檢查），但端到端的 Agent 行為只能人工觀察：

  • 並行執行真的是並行的嗎？
  • 語義記憶召回的時機對不對？
  • Plan mode 的審批流程互動是否流暢？

Claude Code 自身也採用類似策略：核心工具有單元測試，但 Agent 行為依賴人工 QA + 評估套件（eval suite）。
